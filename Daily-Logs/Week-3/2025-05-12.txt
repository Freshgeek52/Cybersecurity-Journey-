**Date**: May 10, 2025 | **Source**: Ravie Lakshmanan, Cybersecurity Reporter 

### Key Takeaways: Google's $1.375 Billion Settlement with Texas

- **Record-Breaking Settlement**:  
  Google agreed to pay **$1.375 billion** to Texas to resolve lawsuits alleging unauthorized **location tracking** and **biometric data collection** (e.g., facial recognition, voiceprints) without user consent. This dwarfs prior settlements:
  - $391 million (40 states, Nov. 2022)
  - $29.5 million (Indiana & Washington, Jan. 2023)
  - $93 million (California, Sept. 2023)

- **Allegations**:  
  - Tracked users' locations even when "Location History" was disabled.  
  - Collected biometric data (facial geometry, voiceprints) without informed consent.  
  - Monitored private searches and movements through Google services.

- **Texas AG's Statement**:  
  Ken Paxton called the settlement a "major win for Texans' privacy," emphasizing that companies will "pay for abusing our trust."

- **Google's Privacy Updates**:  
  - **Maps Timeline Data**: Now stored locally on users' devices instead of Google accounts.  
  - **Auto-Delete Feature**: Allows users to automatically erase location data when Location History is enabled.

- **Context**:  
  - Comparable to Meta's **$1.4 billion Texas settlement** (2023) over biometric data misuse.  
  - Google faces ongoing **antitrust scrutiny** in the U.S. and EU, including calls to break up parts of its business.

 

This summary highlights the financial impact, legal context, user privacy implications, and broader regulatory challenges facing Google.

Access Control Basics
=====================
1.1 Core Concepts
-----------------
Access control is the process of authorizing a subject (such as a user, group, or computer) to access an object (such as a file or folder) on a network or computer. Access control occurs after authentication - the process by which that subject proves their asserted identity. Once they are authenticated, the subject is referred to as a security principal. Security principals - identified by a unique value called an SID - perform actions (if permitted) on objects. Through this process, access control systems help maintain confidentiality by ensuring only authenticated subjects with permission can create, view, or modify objects stored on the network and the local system.

Access Control Models
There are three primary access control models:

Mandatory Access Control (MAC)
Discretionary Access Control (DAC)
Role-Based Access Control (RBAC)
MAC is the strictest of the access control models. With MAC, two security labels (classification and category) get assigned to each subject and object. These security labels must match before a subject gains access to an object. For example, if a file is classified as high security with a category of top secret, then only subjects granted top secret clearance to high-security documents would have access to said object. Outside of the government or military, MAC access control is rarely used.

In DAC, subjects are granted direct permissions to objects. The operating system uses a list of access control entries (ACE) that map a given permission for a given object. In other words, SID + Permission = ACE. Permissions are access representations like read, write, and modify. Thus user John having Allow Read access to an object is one ACE. The complete list of all ACEs is called an access control list (ACL).

 In RBAC, subjects are granted access to objects based on the subject’s role. In this access control implementation, user John would have no access to any object based on his SID alone. Instead, a role is created, and ACEs are granted to this role. In Windows, RBAC is typically implemented using groups. For example, a group called Editors is permitted access to files and folders. John is then added to the Editor's group. Note that simply adding users to groups is not RBAC. The key to RBAC is that groups represent job functions. RBAC works best when there are clearly defined job roles in the organization.

Inheritance 
Security objects can contain other security objects. For example, a folder typically contains other folders. ACEs mapped to the parent folder flow to the child folders, which may be parent objects to additional folders. This downward flow of ACEs is called inheritance. Children inherit security mappings from their parents. Thus if subject John has “ALLOW Read” access to folder C:\Documents, John will also have “ALLOW Read” access to all folders and files created under the C:\Documents folder.

What happens to ACEs when an object is moved or copied to another parent object (e.g., another folder)? On Windows, the object will typically retain any explicit permissions. However, if an object is moved to a new parent folder on a different volume, it will lose all explicit permissions and inherit them from the new parent.

Note: A copied or moved object will inherit permission from the new parent folder and lose inherited permission from the old parent folder.

Windows Permissions
In Windows, there are six standard security permissions:

Full Control
Modify
Read & Execute
List Folder Contents
Read
Write
Each permission can be Allowed or Denied. A Denied permission takes precedence over an Allowed permission. Thus if subject John has ALLOW Modify but DENY Read, John cannot open the file to modify it. Explicit DENYs often have unforeseen consequences. In most cases, it is better to not grant permission than to use a DENY permission.

Note: In addition to the six standard security permissions, there are 14 advanced permissions. However, changing advanced permissions can easily cause permission knots that are difficult to unwind. It is almost always best to stick with the six standard permissions.

To view the Security permissions for a given file or folder in the Windows GUI, you can right-click the object and select Properties from the context menu. Within the Properties window, the Security tab shows the full ACL on the object. This tab is a great tool to visualize and modify ACEs.

Embedded image

Windows also provides a command line tool called icacls. Icacls can display, copy, or modify ALCs on an object. Icacls can show ALCs across all child objects under a parent, making it an ideal tool for validating access permissions.
